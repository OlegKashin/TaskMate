## 0. Сводка ключевых изменений

Для тех, кто уже читал UX Specification v2.1 — в этой версии UX приведён в соответствие с ТЗ v1.4.

1. 🆕 **Source теперь имеет законченный UX для disconnect/reconnect.** `DELETE /sources/{id}` означает soft-disconnect: существующие messages/tasks/Inbox сохраняются, credentials очищаются, новые сообщения не обрабатываются. Повторное подключение того же внешнего источника использует существующую запись Source, а не создаёт дубль (§7, §51 ТЗ).
2. 🆕 **`reminder` теперь полностью реализуемый сценарий.** В ТЗ появилась таблица `reminders`, REST API и срабатывание через существующий `schedule_tick`. UX должен отличать Reminder от Inbox Snooze. При срабатывании создаётся Telegram notification `task_reminder` (§12.1, §25, §28 ТЗ).
3. ⚠️ **`waiting_for` больше не является открытым пробелом.** Intent `create_waiting_for` уже входит в AIResult, а создание доступно из свободного текста; завершение/отмена выполняются через кнопки/REST (§20, §25 ТЗ).
4. ⚠️ **AIResult содержит 18 intents, а не 17.** В расчёт входит `create_waiting_for`; `inbox_classification` отдельно отвечает за категории Inbox (§11, §20 ТЗ).
5. ⚠️ **Перенос задачи между проектами через AI поддержан.** `edit_task.changed_fields.project_hint` можно использовать для назначения проекта или `null` для переноса в Inbox; операция требует подтверждения и поддерживает Undo (§20, §29 ТЗ).
6. 🆕 **Callback-кнопки не передают UUID.** UX не должен зависеть от структуры callback payload; техническая реализация использует короткий DB-backed token `a:<base36(ui_actions.id)>`. Кнопка может истечь или быть уже использована — в этом случае показывается безопасное сообщение (§17, §24 ТЗ).
7. ⚠️ **P1 boundary уточнён.** Email runtime отключён в P0; полноценные Sources, Calendar, Voice, Morning/Evening и Reminders относятся к P1 согласно §54 ТЗ.
8. 🆕 **OAuth flow отражён в UX.** Для Gmail/Yandex/Mail.ru/Google Calendar подключение проходит через browser authorize/callback и возвращается результатом в Telegram; повторный callback с использованным/невалидным state не создаёт credentials (§13.2 ТЗ).
9. 🆕 **Retention-safe UX.** Уже созданные tasks/Inbox/WaitingFor не теряются при retention-purge исходного message; ссылки на message могут исчезнуть, но объект остаётся доступен (§9, §11, §12, §15 ТЗ).
10. 🆕 **Обновлена модель фаз P0/P1.** Командные задачи/проекты — P0; Sources, Calendar, Voice, Morning/Evening, Reminders и proactive analysis — P1; `/analyze` в P0 работает только как информационная заглушка.
11. 🆕 **Локальное хранилище вложений зафиксировано как SeaweedFS.** Вложения сохраняются backend-сервисом через S3-compatible API в локальный persistent volume. Это не меняет пользовательские сценарии: пользователь видит прежние действия «Открыть в источнике» и «Сохранять вложения», а технический endpoint и bucket в интерфейсе не показываются (§34, §39 ТЗ).
## 0.1. Результаты валидации v2.1 → v2.2

В этой версии документ повторно сверен с ТЗ v1.4 по четырём направлениям:

1. полнота покрытия 18 `intent` из `AIResult`;
2. согласованность domain model / REST / UX states;
3. соответствие фазам P0/P1;
4. отсутствие в UX старых решений, которые были исправлены техническими ревизиями v1.2–v1.4.

**Исправлено относительно v2.1:**

1. `waiting_for`: убран статус «пробел контракта» — добавлен полноценный сценарий `create_waiting_for`.
2. `project_hint`: перенос между проектами через AI теперь отражён как поддерживаемый flow.
3. `source disconnect`: убран открытый вопрос — поведение фиксировано как soft-disconnect.
4. `reminder`: сценарий привязан к реальной таблице `reminders`, API и `schedule_tick`.
5. `inbox_classification`: явно отражено, что это независимая от `intent` классификация Inbox.
6. OAuth: UX учитывает browser callback/state и повторное подключение.
7. Source status: отключённый/paused/error source не должен порождать новые messages/AI jobs.
8. P0/P1: Reminders → P1 Assistant в соответствии с §54 ТЗ.
9. Callback UX: кнопки считаются одноразовыми DB-backed actions; UUID доменных сущностей не попадает в `callback_data`.
10. Error/retry UX: промежуточное сообщение редактируется после retry; новые сообщения вместо него не создаются.
## 1. Общая модель взаимодействия ⚠️

Официальный pipeline по ТЗ (§3):

```
Input
  ↓
Persist input                      ← сообщение сохраняется ДО любой AI-обработки
  ↓
Immediate processing status        ← только если операция может быть долгой
  ↓
AI interpretation
  ↓
Action / Proposal / Clarification  ← зависит от confidence-уровня
  ↓
Confirmation (когда требуется)
  ↓
Action
  ↓
Result
  ↓
Undo (15 сек, если операция поддерживает Undo)
```

Отличие от исходной схемы: явно выделен шаг **Persist input до обработки** (гарантирует, что сообщение не теряется даже при недоступности AI) и шаг **Immediate processing status** как условный, но обязательный для долгих операций (§3, §23 ТЗ).

Для каждой операции система должна знать: что инициировало сценарий; что получил ассистент; что он понял (intent + entities + confidence); какое состояние объекта сейчас; что видит пользователь; какие действия доступны; что произойдёт после нажатия; что делать при ошибке; что делать при неоднозначности — этот перечень из исходного UX остаётся верным без изменений.

## 2. Общие UX-правила

### UX-01. Обычный запрос ⚠️ (обновлено под confidence policy §21 ТЗ)

**Trigger:** пользователь пишет текстовое сообщение.

**Input:** например, «Создай задачу подготовить отчёт к пятнице».

**AI interpretation:**
```
intent = create_task
title = "Подготовить отчёт"
due_date = пятница
project = unknown
priority = normal
confidence = 0.92
```

**Дальнейшее поведение зависит от уровня confidence (§21 ТЗ), а не только от самого факта распознавания:**

| Confidence | Что показывает бот | Кнопки |
|---|---|---|
| **high** (≥ 0.85) | Proposal сразу с заполненными полями | `[Подтвердить]` `[Отменить]` |
| **medium** (0.60–0.849) | Proposal с акцентом на возможность правки; в тексте бот явно называет, что вызывает сомнение (поле `reason` из AIResult) | `[Изменить]` `[Подтвердить]` `[Отменить]` |
| **low** (< 0.60) | Proposal **не создаётся**. Бот задаёт уточняющий вопрос (текстом или кнопками с вариантами интерпретации) | зависит от вопроса; после ответа пользователя — повторная интерпретация |

**Message (пример, medium confidence):**
```
Похоже, вы хотите создать задачу:
Подготовить отчёт
Срок: пятница
Проект: Inbox

Не до конца уверен в сроке — уточните при необходимости.
```

**Next:**
- Подтвердить → `TASK_CREATED`
- Изменить → `TASK_EDIT`
- Отменить → `CANCELLED`, ничего не изменяется

**Errors:** если AI недоступен — «Сейчас не получилось обработать запрос. Сообщение сохранено, я попробую снова» (см. раздел 31 про retry policy).

**Edge cases:**
- нет срока → задача создаётся без срока;
- нет проекта → Inbox;
- несколько возможных проектов → показать выбор;
- low confidence → уточняющий вопрос вместо предложения.

### UX-02. 🆕 Долгая операция / промежуточный статус (§3, §23, §51 ТЗ)

Это правило отсутствовало в исходной UX-спецификации как отдельная сущность, хотя без него вся модель подтверждений не работает корректно на практике.

**Trigger:** операция требует STT, LLM или медленного внешнего API.

**Поведение:**
1. Webhook сразу отвечает Telegram `200 OK`, не дожидаясь AI/STT (иначе Telegram может повторно прислать update).
2. Бот немедленно отправляет промежуточное сообщение:
   - для текста — «🤔 Анализирую сообщение...»;
   - для голоса — «🎙 Обрабатываю голосовое...».
3. Celery-задача обрабатывает запрос в фоне.
4. ID этого промежуточного сообщения сохраняется (`ai_processing_jobs.status_message_id`).
5. По завершении **это же сообщение редактируется** (`editMessageText`/`editMessageReplyMarkup`) — новое сообщение не создаётся.
6. При ошибке это же сообщение редактируется в понятный текст ошибки, при необходимости — с кнопкой повтора.

**Важно:** редактируется сообщение бота, а не входящее сообщение пользователя — Telegram API не позволяет редактировать чужие сообщения.

---

### UX-03. 🆕 Единая таблица правил подтверждения (§3 ТЗ)

Исходный документ описывал подтверждение отдельно в каждом сценарии; в ТЗ это сформулировано как глобальное правило, вынесем его явно:

| Категория | Примеры | Подтверждение |
|---|---|---|
| **Без подтверждения** | просмотр, поиск, сводки, статистика (`show_today`, `show_schedule`, `show_stats`, `search_task`, `search_event`) | не требуется |
| **С подтверждением** | создание, редактирование, удаление, смена статуса задачи, создание календарного события | требуется всегда, независимо от confidence |
| **С дополнительным явным подтверждением** | массовое удаление, массовое изменение, отправка email, отмена календарного события | требуется подтверждение + бот явно проговаривает необратимость/масштаб действия |

### UX-04. 🆕 Сообщения без действия (`general_query`, `ignore`)

Не было отдельно описано в v2.0, хотя это 2 из 18 intents (§20 ТЗ).

**`general_query`** — пользователь просто задал вопрос или написал что-то, не требующее изменения данных («Сколько у меня задач в проекте Marketing?», «Что такое Waiting for?»). AI отвечает текстом в `reason`/отдельном текстовом поле; действие не выполняется, подтверждение не требуется (UX-03, категория «без подтверждения»). UX сводится к обычному текстовому ответу бота, без карточки/кнопок.

**`ignore`** — AI определил, что сообщение не требует никакого пользовательского действия (используется прежде всего в контексте proactive analysis, §15/§28 ТЗ). `entities.reason` фиксируется для логирования и отладки.

**❓ Открытый вопрос:** ТЗ не уточняет, должен ли бот при `intent = ignore` явно сообщать пользователю об этом (как в разделе 3, edge case «Не является задачей»), или молчать. Формулировки ТЗ по `ignore` ограничиваются «используется для логирования» — из этого нельзя однозначно вывести UX. До уточнения рекомендуется: при **интерактивном** запросе пользователя (он сам что-то написал боту) — отвечать явно, чтобы не выглядеть «зависшим»; при **proactive analysis** входящих сообщений источника — не создавать отдельное уведомление на каждое `ignore` (иначе Inbox/чат будет засорён), это уже вытекает из того, что `ignore` не входит в список Inbox item_type (§11 ТЗ) и, соответственно, не должен создавать запись в Inbox.

## 3. Создание задачи из сообщения ⚠️

Один из ключевых сценариев продукта, в целом близок к исходному UX, с уточнениями.

**Trigger:** новое сообщение из подключённого источника (доступно только начиная с P1 — сами Telegram/Email источники относятся к P1-фазе, §54 ТЗ).

**Input:** «Иван: Подготовь, пожалуйста, отчёт по продажам к пятнице.»

**AI interpretation (AIResult, §20 ТЗ):**
```json
{
  "intent": "create_task",
  "confidence": 0.91,
  "entities": {
    "title": "Подготовить отчёт по продажам",
    "description": null,
    "due_at": "2026-09-26T18:00:00+03:00",
    "priority": "normal",
    "project_hint": null
  },
  "action": { "type": "create_task", "requires_confirmation": true }
}
```

**State:** `MESSAGE_ANALYZED`

**Message:**
```
📩 Новое поручение
Иван просит подготовить отчёт по продажам к пятнице.

Создать задачу?
Подготовить отчёт по продажам
Срок: пятница
```

**Buttons:** `[Создать задачу]` `[Игнорировать]`, при неоднозначном проекте — дополнительно `[Выбрать проект]`.

**Next:** после подтверждения задача создаётся, `source_message_id` заполняется ссылкой на исходное сообщение (§9 ТЗ) — это то, что даёт возможность отследить происхождение задачи.

```
✅ Задача создана.
Подготовить отчёт по продажам
Срок: пятница
Источник: Иван · Telegram

[Открыть] [Изменить] [Отменить]
```

(«Отменить» здесь — Undo с TTL 15 секунд, см. раздел «Общий паттерн результата».)

**Errors:** AI недоступен → «Не удалось проанализировать сообщение. Оно сохранено, попробую обработать повторно» (сообщение уже персистентно сохранено на шаге Persist input, до вызова AI).

**Edge cases:**

- **Не является задачей** — как в исходном UX, без изменений:
  ```
  Похоже, это информационное сообщение. Создавать задачу не буду.
  [Создать всё равно] [Игнорировать]
  ```
- **Низкая уверенность** ⚠️ — **скорректировано**. В исходном UX здесь предлагалось [Создать]/[Игнорировать], то есть proposal всё равно создавался. По ТЗ (§21) при confidence < 0.60 proposal **не создаётся** — вместо карточки задачи бот задаёт уточняющий вопрос:
  ```
  Не уверен, что это поручение. Это задача, которую нужно создать,
  или просто информационное сообщение?
  [Это задача] [Не задача] [Показать сообщение целиком]
  ```
  Только после ответа пользователя запускается повторная интерпретация и, при необходимости, обычный proposal-флоу.
- **Несколько задач в одном сообщении** 🚫 — **не поддерживается текущим контрактом**. AIResult (§20 ТЗ) возвращает ровно один `intent` и один набор `entities` на сообщение — поля для списка задач в схеме нет. Практически при сообщении с несколькими поручениями LLM вернёт только одну (вероятно, наиболее явную) задачу; остальные будут потеряны без индикации пользователю. Это открытый вопрос продукта: либо расширять AIResult-схему под список задач, либо явно проектировать эту фичу отдельно (не в рамках текущего MVP-контракта). До решения — в спецификации не должно быть сценария «[Создать все] [Выбрать]», так как backend физически не возвращает такие данные.

## 4. Создание задачи вручную ✅ (мелкие уточнения enum'ов)

**Trigger:** Tasks → Создать.

**Input:** «Подготовить презентацию».

**State:** `TASK_DRAFT`

**Message:**
```
Новая задача
Подготовить презентацию
Срок: не указан
Проект: Inbox
Приоритет: normal
```

**Buttons:** `[Создать]` `[Срок]` `[Проект]` `[Приоритет]` `[Отмена]`

Значения приоритета ограничены `tasks.priority` (§9 ТЗ): `low` / `normal` / `high` — в интерфейсе отображаются как 🟢 Низкий / 🟡 Обычный / 🔴 Высокий.

**Errors:** пустое название → «Укажите название задачи» (`title` — обязательное поле, `VARCHAR(500) NOT NULL`).

**Edge case:** не заставлять пользователя заполнять все поля — без изменений.

## 5. Выбор проекта ✅

**Trigger:** проект не определён, либо пользователь нажал «Выбрать проект».

Логика привязки источника к проекту (§42 ТЗ, таблица `source_projects`):
- источник связан с одним проектом → авто-присвоение, без вопроса пользователю;
- источник связан с несколькими проектами → показать выбор именно на этом шаге;
- проекта нет вовсе → Inbox (`project_id = NULL`).

**Message:** «К какому проекту отнести задачу?»

**Buttons:** список активных (`is_archived = FALSE`) проектов пользователя + `[Другой]` + `[Inbox]`.

**Errors:** если проектов нет:
```
У вас пока нет проектов.
[Создать проект] [Оставить в Inbox]
```

## 6. Редактирование задачи ⚠️ (уточнён механизм адресации)

**Trigger:** «Измени срок задачи «Подготовить отчёт» на завтра.»

**AI interpretation** использует механизм `target` (§20 ТЗ) — один из двух форматов:
```json
{ "task_id": "<uuid>" }
```
или
```json
{ "search_hint": { "title_contains": "договор", "recency": "last_mentioned" } }
```
Если пользователь явно ссылался на конкретную задачу (например, только что созданную), AI резолвит `task_id` напрямую. Если это лишь текстовое упоминание — используется `search_hint`, и если по нему находится несколько кандидатов, **backend** (не AI) инициирует выбор у пользователя — «никакого молчаливого произвольного выбора» (acceptance criteria §45 ТЗ).

`entities` для `edit_task` содержит `changed_fields` — объект только с реально изменяемыми полями (`title`, `description`, `due_at`, `priority`), а не весь объект задачи целиком.

**Перенос между проектами через AI поддерживается.** `edit_task.changed_fields.project_hint` может отсутствовать (проект не меняется), содержать имя/подсказку проекта (backend резолвит кандидата по тем же правилам, что и `create_task`) или иметь значение `null` — это команда перенести задачу в Inbox. Если найдено несколько проектов, backend показывает пользователю выбор. Операция требует подтверждения и поддерживает Undo (§20, §29 ТЗ).

**State:** `TASK_UPDATE_DRAFT`

**Message:**
```
Изменить задачу «Подготовить отчёт»:
Срок: сегодня → завтра
```

**Buttons:** `[Сохранить]` `[Отмена]` (форма кнопок дополнительно зависит от confidence-уровня, см. UX-01).

**Errors:** задача не найдена → «Не нашёл задачу «Подготовить отчёт»» + `[Создать новую]` `[Повторить поиск]`.

**Edge case — несколько совпадений:** без изменений, показываются пронумерованные кандидаты.

## 20. Напоминание (`reminder`) 🆕 (разграничено с Inbox-«Отложить»)

**Статус:** реализуемый P1 Assistant-сценарий.

### Reminder ≠ Inbox Snooze

- **Reminder** — отдельная сущность с `title`, `due_at`, опционально `task_id`; при наступлении `due_at` создаётся `notifications.type = task_reminder`.
- **Inbox Snooze** — откладывает конкретный Inbox item до `snoozed_until` и не создаёт отдельный reminder.

**Trigger:** «Напомни мне о договоре завтра в 10:00.»

**AI interpretation:**
```json
{
  "intent": "reminder",
  "confidence": 0.94,
  "entities": {
    "title": "Договор",
    "due_at": "2026-09-26T10:00:00+03:00",
    "related_task_id": "<uuid>"
  },
  "action": {
    "type": "reminder",
    "requires_confirmation": true
  }
}
```

**State:** `REMINDER_DRAFT`

**Message:**
```text
🔔 Создать напоминание?

Договор
Завтра, 10:00
```

**Buttons:** `[Создать]` `[Изменить]` `[Отмена]`

**Result:**
```text
✅ Напоминание создано.
Напомню завтра в 10:00.
```

В момент `due_at` `schedule_tick`:
1. выбирает `pending` reminder;
2. создаёт `notifications(type=task_reminder)`;
3. переводит reminder в `fired`.

**Cancel:** `POST /api/v1/reminders/{id}/cancel`.

**Open UX question из ТЗ v1.4:** нужен ли отдельный список будущих reminders в главном меню/Settings. Минимальный flow — создание через AI и отмена через карточку/REST.
## 21. 🚫 Массовая операция — не описана в текущем AIResult-контракте

**Статус:** ТЗ формулирует общее правило подтверждения для «массового удаления» и «массового изменения» (§3: «Дополнительное явное подтверждение»), но список допустимых `intent` в AIResult (§20 ТЗ) **не содержит** `bulk_update`/`bulk_delete` или аналогичного значения. То есть правило подтверждения для bulk-операций описано, а сам механизм их распознавания из естественного языка — нет.

Практические варианты до момента, пока это не будет уточнено в ТЗ:
1. Реализовать bulk-операции только через явный UI (multi-select в разделе Tasks), не через чат-команду — это не требует расширения AIResult-схемы.
2. Расширить `entities`-схему intent'ов `edit_task`/`delete_task`/`change_task_status`, чтобы `target` поддерживал массовый `search_hint` (например, «все задачи проекта X»), и явно завести это в ТЗ.

```

Перенести все на завтра?
[Перенести 8 задач] [Отмена]
```

## 27. 🆕 Ответ на письмо (`reply_email`, §20, §22 ТЗ)

Отсутствовало в исходной UX-спецификации. ТЗ явно вводит intent `reply_email`, который **всегда** требует подтверждения (`requires_confirmation: true` жёстко, независимо от confidence), и отдельно подчёркивает: «AI не имеет права самостоятельно отправлять email» (§22 ТЗ). Отправка email также входит в категорию действий с **дополнительным явным подтверждением** (§3 ТЗ).

**Trigger:** «Ответь Ивану, что отчёт будет готов завтра» (в контексте письма/сообщения из Inbox) или кнопка `[Ответить]` на Inbox-элементе.

**AI interpretation:**
```json
{ "intent": "reply_email", "entities": { "message_id": "<uuid>", "draft_text": "Иван, отчёт будет готов завтра." } }
```

**State:** `REPLY_DRAFT`

Подготовка черновика — это LLM-запрос, подпадающий под правило **UX-02**: перед показом черновика бот отправляет промежуточное сообщение «🤔 Анализирую сообщение...», которое затем редактируется в итоговую карточку с черновиком.

**Message:**
```
Черновик ответа Ивану:

«Иван, отчёт будет готов завтра.»

Отправить?
```

**Buttons:** `[Отправить]` `[Изменить текст]` `[Отмена]`

**Result:**
```
✅ Ответ отправлен.
Иван · Gmail
```

**Errors:** ошибка отправки (внешний сервис недоступен) → «Не удалось отправить ответ. Черновик сохранён» + `[Повторить]` `[Изменить]`.

**Undo:** не предусмотрен — отправленное письмо нельзя отозвать, поэтому Undo для этой операции не имеет смысла и не входит в обязательный список (§29 ТЗ).

## 30. Удаление проекта ⚠️ (полностью пересмотрено — вопрос был явно решён в ТЗ)

**Это самое значимое расхождение с исходным UX.** В черновике поведение было заявлено как открытый вопрос с двумя вариантами («Удалить проект, оставить задачи» / «Удалить всё»). ТЗ **явно и однозначно** закрывает этот вопрос (§9, §51 ТЗ, acceptance criteria п. 32):

- проект удаляется **физически** (hard delete);
- задачи проекта **никогда не удаляются** вместе с проектом;
- у всех задач `project_id` становится `NULL` — они автоматически остаются доступны в Tasks и переходят фактически в Inbox;
- вариант «удалить всё» **не существует** — это не бизнес-выбор пользователя, а фиксированное поведение системы.

**Важное дополнение, тоже отсутствовавшее в исходном UX:** удаление проекта **не покрывается Undo**, в отличие от операций с задачами. Причина прямо объяснена в ТЗ: сразу после удаления задачи, у которых `project_id` стал `NULL` из-за удаления проекта, неотличимы от задач, у которых `project_id` был `NULL` по другим причинам — надёжно восстановить «какие именно NULL-задачи принадлежали удалённому проекту» невозможно. Это осознанный компромисс, а не недоработка.

**Актуализированный сценарий:**

**Trigger:** «Удали проект Marketing.»

**State:** `PROJECT_DELETE_CONFIRMATION`

**Message:**
```
Удалить проект Marketing?

В нём 12 задач. Они не будут удалены — просто потеряют
привязку к проекту и останутся доступны в общем списке задач.

Это действие нельзя отменить.
```

**Buttons:** `[Удалить проект]` `[Отмена]`

**Result:**
```
🗑 Проект «Marketing» удалён.
12 задач перемещены без проекта.
```
(без кнопки `[Отменить]` — Undo здесь не предусмотрен).

## 31. Обработка ошибки AI / STT ⚠️ (добавлена конкретная retry policy)

**Trigger:** AI или STT недоступны/вернули ошибку.

В исходном UX было сказано только «AI недоступен → сообщение сохранено». ТЗ уточняет retry policy для внешних сервисов (§30 ТЗ):

```
попытка 1 → немедленно
попытка 2 → через 30 сек
попытка 3 → через 2 мин
попытка 4 → через 10 мин
после исчерпания попыток → статус FAILED, пользователь уведомляется
```

**Message (во время retry, если пользователь смотрит в чат — редактируется то же промежуточное сообщение, UX-02):**
```
🤔 Анализирую сообщение...
```

**Message (после исчерпания попыток):**
```
Сейчас не получилось обработать сообщение. Оно сохранено,
я не потерял его — можно обработать позже.

[Повторить] [Оставить на потом]
```

Если у соответствующей `ai_processing_jobs` уже есть `status_message_id` — обновляется именно это сообщение, а не создаётся новое (правило из §30 ТЗ: не создавать бесконечную серию сообщений при повторных ошибках).

## 35. Общий паттерн результата действия ⚠️ (добавлен Undo как обязательный элемент)

Общая схема из исходного UX сохранена и дополнена:

```
[иконка состояния] Что произошло

[объект]
[ключевые изменения]

[следующее логичное действие]
[Отменить]  ← только если операция входит в список с обязательным Undo
```

**Список операций с обязательным Undo (TTL 15 секунд от момента успешного завершения, §29 ТЗ):**
- создание задачи;
- удаление задачи (soft-delete);
- изменение статуса задачи;
- изменение основных полей задачи;
- перенос задачи между проектами/Inbox.

**Операции без Undo (кнопка не показывается вовсе):** удаление проекта, отмена календарного события, отправка email-ответа, массовые операции (пока не реализованы, см. раздел 21) — необратимость либо принципиальна (email), либо состояние невозможно надёжно восстановить (проект).

Не следует завершать сценарий сообщением «Готово» без контекста — правило сохранено без изменений.

**Техническое правило кнопок:** callback-кнопки не содержат UUID доменных сущностей. Backend использует DB-backed `ui_actions`, а в Telegram передаётся короткий token вида `a:<base36(id)>`. Истёкший или уже потреблённый callback не выполняет действие повторно.

## 41. Состояния UX / конечный автомат ⚠️ (дополнена confidence-ветка)

### Task
```text
TASK_DRAFT → TASK_CONFIRMATION → TASK_CREATED
TASK_CREATED → TASK_IN_PROGRESS → TASK_COMPLETED
TASK_DRAFT → TASK_CANCELLED
TASK_CREATED → TASK_DELETED (soft-delete)
TASK mutation → UNDO_AVAILABLE (15 sec) → RESTORED
```

### Inbox
```text
NEW_MESSAGE → ANALYZING → ACTION_REQUIRED → USER_DECISION
   ├── CREATE_TASK
   ├── REPLY (только email)
   ├── CREATE_EVENT
   ├── CREATE_WAITING_FOR
   ├── SNOOZE
   └── IGNORE
```

### Reminder
```text
REMINDER_DRAFT
   ↓ confirm
REMINDER_PENDING
   ↓ schedule_tick at due_at
REMINDER_FIRED
```
или:
```text
REMINDER_PENDING → REMINDER_CANCELLED
```

### Source
```text
CONNECTING → ACTIVE
ACTIVE ↔ PAUSED
ACTIVE/PAUSED/ERROR → DISCONNECTED
DISCONNECTED → CONNECTING → ACTIVE
```

### AI workflow
```text
INPUT
  ↓
PERSIST
  ↓
CLASSIFICATION → ENTITY_EXTRACTION → CONFIDENCE_CHECK
  ├── HIGH   → PROPOSAL → CONFIRM → ACTION
  ├── MEDIUM → PROPOSAL → EDIT/CONFIRM → ACTION
  └── LOW    → CLARIFICATION → RE-INTERPRETATION
```

Для долгой операции:
```text
INPUT → STATUS_MESSAGE → ASYNC JOB → EDIT STATUS_MESSAGE → RESULT/ERROR
```
## 42. Что считать успешным UX ✅

Без изменений относительно исходного документа:

Пользователь понимает: что произошло; что понял ассистент; что изменилось; что нужно сделать дальше.

Пользователь может: исправить ошибку; отменить действие; найти источник; понять происхождение задачи; повторить неудачную операцию.

Ассистент не должен: создавать необратимые действия без подтверждения; задавать лишние вопросы; заставлять пользователя вручную выбирать очевидные параметры; терять входящее сообщение при ошибке; скрывать источник задачи, созданной из входящего сообщения.

## 43. Критические edge cases — актуальный статус по каждому пункту

| № | Вопрос | Статус | Комментарий |
|---|---|---|---|
| 1 | Несколько задач в одном сообщении | 🚫 не поддержано | AIResult задаёт один intent/entity-набор; отдельный multi-action contract не описан |
| 2 | Удаление проекта | ✅ решено | Hard delete проекта; задачи сохраняются с `project_id = NULL`; Undo нет |
| 3 | Отключение Source | ✅ решено v1.4 | Soft-disconnect; данные сохраняются, credentials очищаются, новые messages/AI jobs не создаются |
| 4 | Переподключение Source | ✅ решено v1.4 | Переиспользуется существующая строка по `(user_id, type, external_source_id)` |
| 5 | Конфликт командных действий | ⚠️ ограничен | Один AIResult содержит один intent; несколько независимых содержательных меток идут через `inbox_classification` |
| 6 | Повторная обработка сообщения | ✅ решено | Telegram `update_id` + `(source_id, external_message_id)` + AI job idempotency |
| 7 | Дубли задач между Telegram и Email | ⚠️ частично | Один и тот же external message не дублируется; cross-source semantic deduplication остаётся отдельным решением |
| 8 | Изменение выполненной/отменённой задачи | ❓ открыто | Полный граф разрешённых переходов статусов не зафиксирован |
| 9 | Просроченные задачи | ⚠️ частично | Отображение overdue входит в UX; автоматический reschedule suggestion — расширение |
| 10 | Timezone | ✅ технически / ❓ onboarding UX | `users.timezone` + `TIMESTAMPTZ`; точный onboarding timezone не закреплён |
| 11 | Retry внешних сервисов | ✅ решено | 4 попытки: immediately / +30s / +2m / +10m |
| 12 | Waiting for | ✅ решено v1.3 | `create_waiting_for` создаёт запись; complete/cancel — кнопки/REST |
| 13 | Inbox classification | ✅ решено v1.3 | `inbox_classification` отдельно от intent; `urgent` создаёт notification |
| 14 | Reminder | ✅ решено v1.4 | `reminders` + `schedule_tick`; UX списка будущих reminders остаётся открытым |
| 15 | OAuth callback повторно | ✅ решено | Одноразовый `oauth_states.state_token` + `consumed_at` |
| 16 | Retention-purge source message | ✅ решено | Nullable message links обнуляются; связанные task/Inbox/WaitingFor/AIJob сохраняются |
## 44. Что явно не входит в MVP (§2 ТЗ)

Список для сверки, чтобы UX не проектировался «в вакууме» под то, чего заведомо не будет:

- MAX bot (только Telegram);
- анализ изображений;
- анализ содержимого документов;
- executor / сложные зависимости задач;
- полноценный bidirectional calendar sync;
- smart planning (в т.ч. поиск свободного времени, раздел 16);
- полноценное автоматическое управление временем;
- расширенная аналитика;
- eTime;
- любые функции, явно обозначенные как future extensions.

Ключевой пользовательский loop сохранён без изменений:

Актуализация относительно исходного документа: добавлен раздел Settings как полноправная часть навигации (§3 ТЗ); явно отмечено, что источники (Telegram/Email) относятся к фазе P1, то есть в P0-релизе основной поток — это только «User text/voice → AI ANALYSIS»; убрана предполагавшаяся ветка «поиск свободного времени» как не входящая в MVP.
